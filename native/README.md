# The native shell (desktop and Android)

A Tauri v2 application whose entire job is to give the web app seven things a
browser cannot do. Nothing here decides anything about mail.

## What is in it

| Module | Why it cannot be TypeScript |
| --- | --- |
| `secrets.rs` | OAuth tokens in the OS keychain, not `localStorage` |
| `oauth.rs` | A loopback HTTP listener on an ephemeral port, for the redirect |
| `scheduler.rs` | A background thread that ticks while the window is hidden |
| `files.rs` | A real save dialog, and a path sanitiser |
| `deep_link.rs` | `winnow://` links, registered with the OS |
| `tray.rs` | The tray icon, which is also the only way back once the window hides |
| `updater.rs` | How this copy runs (macOS, AppImage, `.deb`, Android) and installing a newer release |
| `commands.rs` | The command surface. Thin: validate, delegate, stringify errors |

Everything else — the classifier, the sync engine, the store, every pixel — is in
`web/` and runs unchanged in a browser.

## Running

From `web/`:

```sh
npm run tauri:dev
npm run tauri:build                 # .app + .dmg on macOS
npm run tauri:build -- app          # just the .app, no create-dmg needed
```

Tauri 2 requires the `tauri-cli` v2 binary:

```sh
cargo install tauri-cli --version "^2"
```

### Why the build is a script and not `cargo tauri build`

> The previous version of this section claimed that `cargo tauri build` produces
> **no bundle at all** with tauri-cli 2.11 — exits 0, prints `Built application
> at …`, writes nothing under `target/release/bundle/` — and cited a matrix of
> experiments across `tauri.conf.json` bundle settings. **That was wrong.**
> `bundle.active` defaults to `true`, so a bare `cargo tauri build` does bundle;
> verified against tauri-cli 2.11 after the fact. The experiments were almost
> certainly reading a stale `target/release/bundle/` from an earlier run.

The script survives the correction, for the two reasons that were always true:

1. **Bundle kinds are named per host.** Asking macOS for `deb` is not an error
   Tauri reports — it declines to bundle, quietly. So the targets are decided
   here, where a missing one is a sentence.
2. **Success is asserted by looking for the output,** and per kind rather than per
   directory. "The tool said it succeeded" and "a bundle exists where a release
   should be" are different facts, and a bundle directory containing only empty
   subdirectories passes the weaker check while shipping nothing. A release script
   that reports success without shipping anything is worse than one that fails.

It is also where the argument parsing lives, and that was broken: the original
sliced `passthrough.slice(bundles.length)`, which is always an empty slice because
`bundles.length` *is* `passthrough.length` on that branch. Every flag except a
bundle name was silently swallowed, and `npm run tauri:build -- --bundles app`
produced the literal string `--bundles,app` as a bundle name.

### macOS packaging prerequisites

Bundling a `.dmg` needs Homebrew's `create-dmg` — Tauri's `bundle_dmg.sh` is a
thin wrapper around it:

```sh
brew install create-dmg
```

The `.app` needs nothing beyond a Rust toolchain. The script checks for
`create-dmg` up front and says so, because without it the `.app` builds fine and
the `.dmg` then dies inside a vendored bash script with no mention of what to
install.

### The macOS icon

macOS gets its own icon, not the bare planes the other platforms use: macOS 26
(Tahoe) puts any icon that isn't its rounded square into a grey tile.

- `icons/Winnow.icon` is an Icon Composer bundle (the planes floating on light
  Liquid Glass, with Dark set; Tinted and Clear are derived by the system). The
  bundler compiles it into `Contents/Resources/Assets.car` and sets
  `CFBundleIconName`, which needs tauri-cli 2.11+ (tauri-bundler 2.9) and Xcode 26's
  `actool`. Without Xcode 26 the build still works: the bundler logs an error,
  skips the `Assets.car`, and the app uses `icon.icns`.
- `icons/icon.icns` is the fallback for older macOS: an opaque tile on Apple's
  1024 grid (824 px rounded square), so it isn't boxed there either.

Both come from `source-icon.svg` through `icons/make-glass-icon.py` (`pip install
shapely cairosvg pillow`). `cargo tauri icon` regenerates everything else, but it
would overwrite `icon.icns` with the bare planes: rerun the script after it. The
release workflow fails the macOS build if the `.app` lacks the `Assets.car`.

### Apple Silicon

The bundle built here is whatever the host toolchain targets — x86_64 on an Intel
Mac, `aarch64` on Apple Silicon. For a universal binary:

```sh
npm run tauri:build -- --target universal-apple-darwin
```

which needs both targets installed: `rustup target add aarch64-apple-darwin
x86_64-apple-darwin`.

## Android

The same crate, built for Android by `cargo tauri android build`. The Android
Studio project is `src-tauri/gen/android`, generated by `cargo tauri android init`
and committed (Tauri's guidance; its own `.gitignore` keeps the build outputs out).
`tauri.android.conf.json` overrides the identifier for Android only:
`app.winnow.android`. The desktop identifier (`app.winnow.desktop`) and the
keychain service name in `secrets.rs` are unchanged.

What differs from desktop:

| Piece | Android |
| --- | --- |
| Tray, autostart, single-instance, window state, hide-on-close | Compiled out with `#[cfg(desktop)]` (and target-gated in `Cargo.toml`) |
| Secrets (`secrets.rs`) | `keyring` has no Android backend. [`android-native-keyring-store`](https://crates.io/crates/android-native-keyring-store), from the keyring project: AES-GCM with a key held in the Android Keystore, ciphertext in the app's private SharedPreferences. Same `secrets_set` / `secrets_get` / `secrets_delete` commands. It finds the app through `ndk-context`, which Tauri's runtime (tao) initialises, so there's no Kotlin glue |
| Sign-in (`oauth.rs`) | Unchanged: the loopback listener binds `127.0.0.1` inside the app and the system browser opens through `opener`. Needs a **Desktop app** OAuth client, the same as desktop |
| Background sync | Off (`backgroundSync: false`): Android pauses a backgrounded webview, so ticks would land nowhere. Sync runs while the app is open |
| Saving attachments | The system save picker returns a `content://` URI; `files.rs` writes it through `tauri-plugin-fs` (Android only) |
| Unread badge | No-op |
| Back button | The webview takes Back over (`onBackButtonPress`, in `desktopPlatformExtras.onBackButton`) only while something is open, and closes the topmost layer: a popover or menu, a sheet, the composer (parked as a draft), the sidebar, Settings, the open message. At the bare list it hands Back to Android, which leaves the app as usual; `capabilities/android.json` grants `exit` for a press that lands as the last layer closes. The order is `web/src/ui/backLayers.ts` |
| System bars | `MainActivity.kt` pads the content view by the status bar, gesture bar, cutout and keyboard, because the WebView reports no `safe-area-inset-*` under Android 15's forced edge-to-edge |

Building locally needs JDK 17+, the Android SDK and NDK (`ANDROID_HOME`,
`NDK_HOME`) and the Rust targets (`rustup target add aarch64-linux-android
armv7-linux-androideabi x86_64-linux-android i686-linux-android`):

```sh
cd native
cargo tauri android build --apk    # gen/android/app/build/outputs/apk/universal/release/
```

A type check needs none of that: `cargo check --target aarch64-linux-android`
in `src-tauri` links nothing, so it runs without the NDK (CI does this on PRs that
touch `native/`).

### Android signing

**Native Google sign-in and your own key.** The setup guide's optional Android step
registers an Android OAuth client for `app.winnow.android` and the APK's signing
certificate. Google accepts each package name and certificate pair in one Cloud
project only, so with the official release key only the first person to register it
can use native sign-in. A build signed with your own keystore (below, or
`keystore.properties` for a local `cargo tauri android build --apk`) has a
certificate only you hold, and the step shows its SHA-1. Everyone else signs in
through the browser, which needs none of this.

`release.yml` signs the Android build with a release keystore whenever four
repository secrets exist, and needs no edit to turn it on. Until they do (and on
forks, which never see them), it falls back to the runner's **debug key**, names
the APK `…_android-universal-debug.apk`, and says so in the job summary; the
build doesn't fail. With them, it ships `Winnow_<version>_android-universal.apk`
and puts a signed `.aab` (for a future Play Store listing) in the workflow
artifact. Either way the job summary lists each file's SHA-256 and the signing
certificate's SHA-256, so a download can be checked with
`apksigner verify --print-certs` or `sha256sum`.

`gen/android/app/build.gradle.kts` reads the signing values from the environment
(`ANDROID_KEYSTORE_PATH`, `ANDROID_KEYSTORE_PASSWORD`, `ANDROID_KEY_ALIAS`,
`ANDROID_KEY_PASSWORD`) or, for a local build, from an untracked
`gen/android/keystore.properties` (`storeFile`, `password`, `keyAlias`,
`keyPassword`); nothing is hardcoded, and keystores are gitignored.

To turn it on, once:

1. Make the keystore, outside the repo (JDK 17+ `keytool`; it asks for a password):

   ```sh
   keytool -genkeypair -v -keystore winnow-release.jks -storetype PKCS12 \
     -keyalg RSA -keysize 4096 -validity 10950 -alias winnow
   ```

   A PKCS12 keystore has one password for the store and the key, so the key
   password is the same as the keystore password.

2. Base64 it for the secret:

   ```sh
   base64 -w0 winnow-release.jks > winnow-release.jks.b64    # Linux
   base64 -i winnow-release.jks -o winnow-release.jks.b64    # macOS
   ```

   ```powershell
   # Windows PowerShell
   [Convert]::ToBase64String([IO.File]::ReadAllBytes("$PWD\winnow-release.jks")) | Set-Content -NoNewline winnow-release.jks.b64
   ```

3. Add four repository secrets (**Settings → Secrets and variables → Actions →
   New repository secret**), then delete the `.b64` file:

   | Secret | Value |
   | --- | --- |
   | `ANDROID_KEYSTORE_BASE64` | The contents of `winnow-release.jks.b64` |
   | `ANDROID_KEYSTORE_PASSWORD` | The password you gave keytool |
   | `ANDROID_KEY_ALIAS` | `winnow` (the `-alias` above) |
   | `ANDROID_KEY_PASSWORD` | The same password as `ANDROID_KEYSTORE_PASSWORD` |

   The next `v*` tag builds a signed APK. GitHub masks every secret's value in
   logs, so with the alias `winnow` a lowercase "winnow" in the Android job's log
   shows as `***`; that's cosmetic.

**Back up the keystore and its password** somewhere that isn't this repo and isn't
only GitHub (secrets can't be read back out). Android only installs an update
signed with the same key as the installed app: lose either and no existing install
can ever be updated in place again; every user would have to uninstall and
reinstall. Never commit the keystore or paste it anywhere public.

**Moving from the debug APK:** anyone who installed an earlier `-debug` APK must
uninstall Winnow once before installing the first signed one, because the
signatures don't match (uninstalling signs them out). After that, signed updates
install over each other.

## Cutting a release

Run **Actions → Cut release → Run workflow** on `master`. Pick `patch`, `minor`,
`major` or an exact version, optionally a pre-release suffix (`beta.1` tags
`v1.2.0-beta.1` and publishes it as a pre-release), and leave **publish** on.

It runs `web/scripts/bump-version.mjs` to set the version in all six manifests,
commits `Release vX.Y.Z` to `master`, tags it, and dispatches CI on the tag. A push
made with `GITHUB_TOKEN` triggers no workflows, so the dispatch replaces the usual
tag push. When CI passes it hands off to `release.yml`, which builds the draft. Its
last job publishes the draft only if all four bundles are attached (plus the updater
files and `latest.json` when the signing key is set, see "Updates") and the APK is
release-signed. Anything missing (Android is allowed to fail) leaves
the draft for you to finish or publish by hand.

Pushing a `v*` tag by hand works the same way: bump the manifests yourself
(`node web/scripts/bump-version.mjs X.Y.Z`, commit), push the tag, and once CI
passes the release builds and publishes behind the same guards (all four bundles,
a release-signed APK), or stays a draft if one is missing. A `-suffix` tag is a
pre-release; anything else becomes Latest.

## Updates

The web layer finds a newer release (`web/src/core/updates/`, GitHub's
`releases/latest`) the same way on every host; `updater.rs` installs it the way this
copy runs:

- **macOS, AppImage** (`$APPIMAGE` set): `tauri-plugin-updater` reads
  `https://github.com/hxmbl/winnow/releases/latest/download/latest.json`, checks the
  download against `plugins.updater.pubkey` in `tauri.conf.json`, swaps the app and
  restarts. The universal macOS tarball serves both `darwin-aarch64` and
  `darwin-x86_64`.
- **`.deb`** (binary under `/usr`): never replaced in place, since dpkg owns it.
  The `.deb` is downloaded to Downloads and opened with the system installer.
- **Android**: `UpdatePlugin.kt` downloads the APK and opens the package installer
  (`REQUEST_INSTALL_PACKAGES`, the existing FileProvider). It installs over the
  running app only when signed with the same release key, so a `-debug` APK is
  never offered.

**Signing.** `release.yml` signs the updater artifacts with two repository secrets:
`TAURI_SIGNING_PRIVATE_KEY` (the key file's contents) and
`TAURI_SIGNING_PRIVATE_KEY_PASSWORD`. With them, a tag build also attaches
`Winnow_<v>_universal.app.tar.gz`, its `.sig`, the AppImage's `.sig` and
`latest.json` (whose `notes` are the release body), and the publish guard requires
them. Without them the release builds and publishes as before, with no `latest.json`;
installed apps then open the release page instead of updating themselves. The public
key in `tauri.conf.json` must match the private key: replacing the key means every
installed copy stops accepting updates until it is reinstalled by hand. Generate a
pair with `npx @tauri-apps/cli signer generate -w winnow.key`.

## The command surface

Every command in `commands.rs` has a binding in `web/src/platform/desktop.ts`
and a working browser equivalent except the ones documented as native-only. When
you add a command, add both halves, or the platform interface grows a method
with no browser implementation — which is the whole thing the interface is
designed to prevent.

```
app_info                    what this build can do
secrets_set / _get / _delete   the keychain
oauth_begin / _await / _cancel  the loopback sign-in
notify_messages             per-message notifications with Reply, Delete, Mark read
open_external               the system browser, https only
save_attachment             a save dialog
set_unread_badge            dock badge, tray tooltip, window title
set_background_sync         start, retune or park the ticker
request_notification_permission
update_runtime              how this copy runs: macos, appimage, deb, android, manual
update_install              Tauri's updater: install and restart (macOS, AppImage)
update_download_deb         download a release .deb and open the system installer
update_install_apk          download a release APK and open Android's installer
```

## The loopback port

`oauth_begin` receives the authorize URL with `__WINNOW_LOOPBACK_PORT__` where
the port goes, binds a listener, substitutes the port it actually got, and hands
back the finished URL. A URL without the placeholder is refused rather than
silently accepted — see the comment on `PORT_PLACEHOLDER` for why that failure
would be so expensive.

## Parsing the request target

`serve` splits the request target on `?` and hands the path to `Url::set_path`
and the query to `set_query`, separately.

This is not a detail. The version that folded the whole target into `set_path`
produced a URL whose `query_pairs()` was always empty, so the listener answered
every request with a 204 and never once read a `code` or an `error`. It did not
crash or report anything wrong: it waited, and the sign-in timed out five
minutes later with a message blaming the user's network.

The tests around it had passed the whole time, because they checked that the
listener *answered* a request and not that it *understood* one. A malformed target
is now answered with an error page rather than dropped, for the same reason: a
connection that hangs open is indistinguishable from a listener that is not there.

## Field names across the IPC boundary

Tauri rewrites **argument** keys from camelCase to snake_case, and never rewrites
**return values** — those go through plain serde using the struct's own field
names. So a struct declared `authorize_url` in Rust and read as `authorizeUrl` in
TypeScript yields `undefined`, and nothing anywhere reports an error.

Three bugs shipped that way before the tests that now catch them existed:

- `AppInfo`'s capability flags all arrived `undefined`, so `backgroundSync` read
  as absent and the settings panel's entire Background section was gated on it. A
  feature that was implemented, permissioned and unreachable.
- `oauth_begin`'s reply was read as `authorizeUrl`, so `open_external` was called
  with `url: undefined`, IPC rejected it with "missing required key url", and
  desktop sign-in was impossible.
- `notify_new_mail`'s (since replaced by `notify_messages`) `message_ids` was sent as `messageIds`, which *deserialised
  successfully* into a struct with `#[serde(default)]` — as an empty vec. No error
  at all, and a notification click could never know which conversation to open.

`serde(rename_all = "camelCase")` is not the fix for the first of these: it
produces `nativeOauth`, not `nativeOAuth`. Every field carries an explicit
`#[serde(rename = …)]`, and `web/src/platform/platform.test.ts` asserts the
wire shapes the UI actually reads.

## Three fixes worth knowing about

Each of these was a hang, a deadlock, or a silent no-op, and none of them
produced an error at the call site.

- **`oauth_await` no longer unregisters its port on entry.** It did, so `oauth_cancel`
  had nothing to cancel and Cancel did nothing — the sign-in could not be stopped.
- **`save_attachment` is `async`.** The save dialog blocks; called synchronously from
  the command thread it deadlocked the main thread, so the dialog could not be
  dismissed.
- **`Reopen` reveals the window,** and `focusWindow` calls `unminimize` before
  `show` and `setFocus`. `setFocus` on a minimised window focuses nothing visible,
  and `unminimize` needed a capability that had not been granted — so it was
  rejected, and being first in the sequence, it stopped the other two running.
  Every deep link and every tray click on a running app therefore did nothing.

## Closing the window hides the app

The inbox client is meant to keep syncing, so `CloseRequested` hides rather than
quits. That makes the tray load-bearing rather than decorative: it is the only
way back in, and the only way to quit. If you remove the tray, remove the hide.

The corollary is that showing the window has to be deliberate. It is configured
`visible: false` so nobody sees a white rectangle while the webview boots, and
`on_page_load` reveals it once the page has actually finished — the only moment
there is something to look at. Before that hook existed, a normal launch produced
a tray icon and no window at all.

`--minimized` skips the reveal: that is how the autostart entry point launches,
and a login item that opens a window over whatever the user is doing is exactly
the behaviour people switch off.
